# 건물 3D 로딩 작업 재개 — 목표 미달, 미배포

사용자 요청에 따라 `fix/frame-budget-20261003`의 작업을 이어 진행했다. 루트 main 작업 폴더의 다른 수정은 건드리지 않았다. 기준은 이 브랜치의 `48bf12d`와 당시 생성돼 있던 준비 맵 `117f76d53cf95fdc66c0`이다. 이전 운영 버전과의 비교가 아니다.

## 유지한 변경

- 이웃 건물의 indexed geometry, 법선, UV, 색상을 기존 scene worker에서 생성하고 배열 소유권을 전송한다. 워커가 없거나 실패하면 기존 계산으로 복구한다. 난수 소비 순서, 건물 수, 높이, 구멍, 재질, 해상도를 유지한다.
- 자체 건물의 경계가 확정되면 지면 그리드를 먼저 요청해 후속 재질 준비와 겹친다. 취소된 결과는 GPU 객체를 생성하지 않는다.
- 검증된 법선맵을 사용하는 외벽과 석재 painter에서 사용하지 않는 높이 캔버스와 외벽 blur를 생략한다. 준비 맵이 없으면 원래 높이 생성 및 법선 계산을 실행한다.
- painter 해시에 맞는 준비 맵 35개와 manifest를 다시 생성했다. PNG 35개는 이전 준비 파일과 SHA-256까지 같다. 추가 자산 총량은 manifest 포함 3,773,163바이트다.
- 성능 harness에 기존 production build 재사용을 추가했다. 숨긴 rail / on-page painter처럼 빌드에 들어가는 옵션이 다르면 재사용을 거부한다. 각 실행은 새 브라우저에서 진행한다.

## 반복 측정

Edge 155.0.4283.33, production harness, 동일 컴퓨터, 자체 건물 9개와 이웃 건물 275개, high, 고정 렌더 배율 1.5. 서버/API는 같은 고정 응답을 사용한다. 20ms 초과 rAF 간격을 드랍으로 집계한다. 캡처는 전체 타이밍 기록 이후 실행한다.

최초 표시 중앙값은 1749→1587ms로 **9.3% 단축, 속도 비율 1.10배**다. 모델 구축 중앙값은 963→817ms다. 3회에 불과하고 변동이 크므로 모든 실제 단지나 장치에서의 개선을 입증하는 결과는 아니다.

후보의 초기 로딩 드랍은 9 / 8 / 9회다. 첫 실행에서는 단지 전환 중에도 1회 발생했다. 나머지 일반 조건 구간은 세 실행에서 모두 20ms 이내였지만 **전체 드랍 0은 아니다.** 세 후보 모두 `check-complex-frames.py`가 실패(exit 1)한다. 3배 목표에 해당하는 이 기준의 583ms에도 미달이다. 마우스 무지연 역시 미달이다.

CPU 4배 제한, CDN 5초 지연, 숨긴 rail, WGSL feature marker 제거를 적용한 별도 실행: 최초 표시 3023ms, 로딩 최대 간격 266.8ms, 최대 입력 지연 254.6ms, 전체 드랍 122회. WebGPU high, 숨긴 뷰 렌더 0, 브라우저 오류 0이었다. 이 실행은 일반 조건 전후 비교에 섞지 않는다.

WebGL 호환 실행: 최초 표시 1737ms, 로딩 최대 간격 850.2ms, 최대 입력 지연 351ms, 전체 드랍 32회, 브라우저 오류 0. 기능 호환은 확인했지만 성능 목표는 실패했다.

## 정확도와 수명 검증

- 별도 원본 구현과 810가지 지형/높이/층수/윤곽/구멍 입력을 비교했다. 정점, 법선, UV, 인덱스, 색상이 byte-exact였고 실제 structuredClone 전송으로 원본 버퍼가 분리됐다.
- 실제 브라우저 worker에서 275개 건물, 258,500바이트를 비교했다. 준비 중 닫기, 다시 열기, worker 미지원 fallback이 통과했다.
- 원래 painter와 워커/준비 맵의 텍스처 50개 비교: 최대 차이 1/255, 평균 0.00006143, 오류 0으로 기존 화질 기준을 유지했다.
- GPU 분할 업로드와 채널 packing의 4가지 크기/방향 조합은 픽셀 차이 0, 검증 오류 0이었다.
- Node 회귀 28개, TypeScript 검사, 제품 production 빌드, `git diff --check`가 통과했다. 기능 검사 통과와 성능 목표 통과를 구분한다.
- overview의 계측 GPU 버퍼 바이트는 비교 양쪽 모두 25,980,356이었다. 이 변경으로 메모리 감소를 주장하지 않는다. 기존 전체 메모리 반복 검사 미달을 해결했다고도 판정하지 않는다.

## 제외한 실험과 다음 병목

이웃 worker 요청을 모든 paint보다 먼저 시작한 후보는 최초 표시 1812 / 2094 / 1861ms로 개선이 확인되지 않아 앞당긴 요청을 제거했다.

부하 추적에서 detail 이미지의 `copyExternalImageToTexture` 호출 하나가 28.1ms였다. ImageDecoder로 canvas 없이 디코딩하는 실험은 CPU 캔버스와 같은 픽셀을 얻었지만, 실제 GPU 업로드와 mip 비교에서 roof mip 0의 차이가 2/255로 기존 허용 범위를 초과했다. 이 경로와 worker를 최종 코드에서 제거했다. 기준을 늘리지 않았다. 실험 소스와 이유는 `tmp/detail-decoder-rejected-20261003.json`에 보존했다.

남은 핵심은 첫 device/파이프라인 준비와 GPU-backed 이미지의 raster/copy 작업을 UI 및 프레임 기록과 직접 대응시켜 제거하는 것이다. CPU 계산을 워커로 옮기는 것만으로는 브라우저 GPU 프로세스의 멈춤을 없애지 못했다. 전체 구간 20ms, 3배 로딩 및 로딩 중 입력 기준을 모두 통과하기 전에는 달성/완료로 보고하지 않는다. 이 후보는 운영에 병합하거나 배포하지 않았다.
