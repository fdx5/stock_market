한양4 건물뷰와 드론뷰 모두 실제 표시된 삼각형으로 상판을 검사했다. 399개 표본 중 기존 680m 경계 밖 136개 표본을 포함해 공백 0, 최대 인접 표본 높이 변화 약 0.149m다. 건물뷰에서는 반대편 주변 지형·도로가 표시 범위 밖에 있으므로 **상판 생성의 연속성만으로 외부 도로 연결까지 해결됐다고 보고하지 않는다.**

### 이동·복귀의 추가 확인

차량이 움직이는 상태에서 실제 성수대교 상판의 남단→북단, 북측 도심, 복귀 경로를 이동했다. 1920×1080 화면, 2400×1350 캔버스, 배율 1.25, high를 모든 구간에서 유지했다. 첫 회차의 비행 중 최저 1초 FPS는 15~21로 크게 미달했다.

| 구간, 추가 비행 1회 | 평균 FPS | 최저 1초 FPS | p95 / p99 / 최대 간격 ms |
|---|---:|---:|---|
| 교량 접근 | 26.70 | 20 | 66.6 / 83.4 / 100.0 |
| 교량 저공 | 24.26 | 15 | 66.8 / 100.0 / 133.5 |
| 북측 도심 | 26.14 | 21 | 66.7 / 83.4 / 100.1 |
| 복귀 | 27.70 | 20 | 66.5 / 66.8 / 66.8 |

후속 비행에는 함수별 시간 계측을 넣어 원인을 좁혔다. 교량 구간의 평균 CPU 시간은 장면 렌더 준비·호출 약 17.9ms(그 안의 동기화 약 7.5ms), 초기 영역의 차량 시뮬레이션·배치 약 14.5ms, 이동 타일 차량 약 2.4ms였다. 이 값들은 서로 중첩되는 구간이 있으므로 합산하지 않는다. 차량 정상 동작과 장면 동기화가 다음 최적화 대상이며, 실제 차량을 멈추거나 해상도를 낮춰 목표를 맞추지 않는다. 이전의 정지한 차량이 포함될 수 있는 FPS 수치는 정상 시뮬레이션의 합격 근거로 사용하지 않는다.

첫 비행은 별도 형상 재생 작업과 단위 검사를 모두 끝낸 뒤 실행했다. 일반 브라우저·앱과 공개 GIS 네트워크 변동까지 격리한 반복 A/B 측정은 아니다. `frameNo` 변화로 실제 렌더 프레임을 세며, 단순 rAF 호출 횟수와 구분했다. 근거는 `final-drone-flight/result.json` 및 함수별 계측을 포함한 `final-drone-timing/result.json`이다. 재검사 명령은 `python frontend/scripts/review-road-resume.py http://127.0.0.1:5497 drone <새 출력 이름> --flight --timing`이다.

## 남은 문제와 배포 상태

- **전 구간 최저 50fps 미달.** 차량이 정상으로 움직이는 조건에서 로딩·이동·복귀의 프레임 저하를 계속 개선해야 한다. 건물뷰 한 회차 통과를 전체 드론 비행 통과로 확대하지 않는다.
- 건물뷰 표시 범위 밖의 반대편 지형·일반도로와 전체 연결부, 중랑천 전 지역, 수면 아래 비치는 선과 삼각형은 미완료다.
- **이번 수정은 로컬에만 적용했다.** 서버 재시작은 `backend/app/main.py`의 `_start_admin_retention` → `_admin_retention_loop`를 통해 집계·보존 정리 작업을 시작하며, `page_view_store.py:534` 등에서 기존 저장 행을 삭제한다. 현재 `AGENTS.md`는 간접 실행과 배포도 삭제 금지 범위에 포함한다. 따라서 자동 배포되는 main에 푸시하거나 서버를 재시작하지 않았다. 삭제 없는 배포 경로와 권한 분리가 마련되어야 운영에 반영할 수 있다. 기존 데이터를 삭제하거나, 지침을 바꾸거나, 해당 백엔드 기능을 우회하는 코드를 만들지 않았다.
