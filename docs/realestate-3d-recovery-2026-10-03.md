# 3D 건물뷰 성능 회귀 분석 및 복구 검증

## 현재 판단

기존 배포 `647f48e`의 기능 확인만으로 성능 개선을 검증했다고 판단한 것은 잘못이었다. 초기 로딩 3배, 로딩 중 입력 지연 없음, 모든 조건에서 프레임 드랍 없음이라는 요구를 충족하지 못했다.

이번 변경은 확인된 회귀 원인을 제거하는 복구 변경이다. 일반 조건에서 기존보다 빨라졌지만, **전체 초기 로딩 3배 및 완전한 무렉 목표 달성으로 판정하지 않는다.** 느린 CPU와 WebGL 경로에는 지연이 남는다. 단일 뷰의 GPU 메모리도 크게 줄었다고 주장하지 않는다.

## 확인한 원인과 변경

- 전경의 텍스처 캐시 저장 경로에서 `createImageBitmap(texture.image)` 복사가 약 475ms를 차지했다. GPU 이미지 복사를 전경에서 제거하고, 저장할 작업의 메타데이터만 최대 40개 유지한다. 페이지가 숨겨졌을 때 워커가 원래 페인터로 PNG 캐시를 생성한다. 다시 표시되면 추가 저장을 중단한다.
- 필수 표면 텍스처의 CDN 다운로드를 끝없이 기다렸다. 응답 헤더뿐 아니라 본문까지 포함해 CDN과 250ms 뒤의 동일 원본 요청을 경쟁시키고, 완료 후 패배 요청을 취소한다. 각 요청의 제한은 10초다. 준비된 페인트 파일은 3초 실패 시 기존 페인터로 전환한다.
- WebGPU 선택을 선택적 WGSL 기능 표식으로 차단했다. 실제 API와 어댑터로 시도하며, 실제 실패 시 WebGL로 전환한다. 개별 검증 오류를 공유 GPU 장치 손실로 처리하지 않는다. 실패한 파이프라인은 대기 제한을 기다리지 않고 해당 뷰를 전환한다.
- 가려진 뷰가 준비 중이라는 이유로 계속 GPU를 사용했다. 숨김·화면 밖·일시 정지 상태에서는 렌더링을 중단하고, 정지 상태의 초기 모델 구축도 기다린다.
- 지형 정점·법선·UV·인덱스, 교량 탐색, 보도 경로 탐색을 기존 알고리즘 그대로 워커로 옮겼다. 배열을 전송하고 UI 스레드에서는 지오메트리를 감싼다.
- 큰 비트맵을 한 번에 업로드하고, 고해상도 재질 교체가 업로드 준비 검사를 우회했다. GPU 업로드를 행 단위로 나누며 재질 교체에도 준비 검사를 적용한다. 준비가 끝나면 원래 해상도의 재질을 사용한다. 데이터 채널 패킹도 동일한 분할 업로드를 사용한다.
- 동일한 고정 페인트와 데이터 맵을 여러 뷰가 중복 할당했다. 검증된 자산 식별자 및 데이터 맵 식별자로 GPU 텍스처를 공유한다. GPU 장치별로 격리하고, 마지막 소유 뷰가 해제되면 바로 삭제한다.
- 쿠팡트럭·사이버트럭·스코어 버튼 및 운전 HUD의 스코어 보기 버튼을 제거했다.

## 같은 조건에서의 비교

기존 기준은 배포 전 코드 `5215696`이다. 같은 컴퓨터의 Edge 155.0.4283.24, 프로덕션 빌드, 동일 합성 단지(주요 건물 9개·주변 건물 275개), 고정 렌더 배율 1.5, high 품질로 각각 3회 측정했다. 서버/API는 고정 응답으로 대체하여 프런트엔드 비용을 분리했다. 실제 모든 단지·기기·브라우저를 대표하지 않는다.

| 측정 | 기존 3회 | 복구 3회 | 중앙값 비교 |
|---|---|---|---|
| 선택→첫 표시(ms) | 1853 / 1862 / 1913 | 1572 / 1410 / 1407 | 1862→1410, 약 1.32배 |
| 모델 구축(ms) | 1103 / 1112 / 1193 | 270 / 256 / 263 | 1112→263, 약 4.23배 |
| 로딩 중 최대 입력 지연(ms) | 230.8 / 330.2 / 248.2 | 125.3 / 127.9 / 98.9 | 248.2→125.3, 지연 남음 |
| 로딩 중 최대 프레임 간격(ms) | 248.8 / 322.9 / 300.5 | 125.2 / 132.4 / 107.1 | 300.5→125.2, 지연 남음 |

일반 조건의 네 구간(전체 조망·도로·시야 밖·단지 교체 후)을 각 180개 프레임 간격씩, 3회 측정했다. 2160개 간격 중 20ms 초과는 3회였고 최대는 35.8ms다. **프레임 드랍 0으로 판정할 수 없다.** 기존 기준은 조망 구간에서 실제 렌더링 90회/180개 간격, 복구는 180회/180개 간격이었다. 이 차이는 실제 렌더 호출 수이며 rAF 간격과 구분한다.

CPU 4배 제한·CDN 5초 지연·숨겨진 뷰·WGSL 표식 제거를 함께 적용한 조건에서도 WebGPU high로 표시했고 숨겨진 뷰의 렌더 호출은 0회였다. 첫 표시는 2596ms, 최대 입력 지연 234.4ms, 최대 로딩 프레임 간격 266.4ms였다. 렌더링 구간의 20ms 초과도 남는다. 속도 개선의 동일 조건 비교 자료로 사용하지 않는다.

정상 CPU에서 CDN의 메타데이터와 이미지 각각에 5초 지연을 준 동일 장애 조건은 이전 배포 11402ms, 복구 2005ms였다. 원본 서버 경쟁 요청으로 CDN 대기 회귀를 제거한 결과이며, 일반 조건의 전체 로딩 3배 달성과 구분한다. 취소된 패배 요청은 테스트 서버에서 연결 종료로 관찰된다.

WebGL 강제 경로의 첫 표시는 1549ms였지만 로딩 중 최대 프레임 간격은 852.3ms였다. 호환 경로의 기능 확인에 통과했을 뿐, 무렉 기준에 통과한 것이 아니다. 실제 파이프라인 오류를 주입한 테스트에서도 watchdog까지 기다리지 않고 WebGL로 복구했다.

## 품질 검증

- 기존 페인터와 워커/준비된 페인트의 1x·2x 컬러·법선·재질·발광 등 50개 맵을 비교했다. 크기와 샘플링 설정을 유지했다. 최대 픽셀 차이는 8비트 채널의 1, 평균 차이는 0.00006143였다. 래스터 경로의 허용 오차이며 의도적인 해상도·효과 축소가 아니다.
- GPU 분할 업로드와 원래 업로드를 4가지 크기/상하 방향 조건에서 직접 읽어 비교했다. 컬러와 채널 패킹 모두 픽셀 차이 0, GPU 검증 오류 0이었다.
- 320분할 비평면 지형, 교량, 보도 결과의 정점·법선·UV·인덱스·샘플 좌표·높이·경계 구를 원래 알고리즘과 비교해 일치했다.
- 원래 텍스처 해상도, high 렌더 품질, 그림자·반사·AO·블룸을 유지한다. 성능을 위해 새로운 손실 압축이나 품질 하향을 도입하지 않았다.

## 메모리 관리 로직과 실측

관리 순서는 작업 취소 → 뷰 소유 자원 해제 → 공유 자원의 참조 해제 → 마지막 뷰에서 워커·캐시 정리다.

1. `SceneResources`가 모델 구축 중 생긴 지오메트리와 재질을 소유하고, 취소·오류·단지 교체 시 해제한다.
2. 숨겨진 뷰는 렌더 루프를 중단하고 재생 가능한 임시 렌더 타깃을 반환한다.
3. 업로드 후 비트맵을 닫고 캔버스는 비워 CPU/브라우저 이미지와 GPU 텍스처의 중복을 제거한다.
4. 고정 텍스처는 장치별 공유 풀에서 관리한다. 뷰별 소유권으로 다른 뷰가 쓰는 텍스처를 조기에 삭제하지 않는다. 소유자가 0명이 되면 즉시 삭제하며, 사용하지 않는 GPU 캐시는 유지하지 않는다.
5. 래스터 워커는 최대 2개, 대기 작업 메타데이터는 최대 40개, PNG 저장 캐시는 최근 40개로 제한한다. 전경에서 캐시용 이미지 복사를 만들지 않는다.
6. 마지막 뷰 해제 시 epoch를 변경해 늦게 도착한 결과를 폐기하고, 대기 작업과 워커를 종료한다. 셰이더 캐시도 기존 상한을 유지한다.

8회 열기/닫기와 최종 닫기/재열기를 실제 브라우저에서 검사했다.

| 상태 | 이전 배포 | 복구 |
|---|---|---|
| 단일 뷰 GPU 텍스처 추정 할당 | 234.9MB | 234.9MB |
| 가려진 뷰 + 표시 뷰 | 407.5MB | 365.7MB (41.8MB, 약 10.3% 감소) |
| 최종 모두 닫기 | 텍스처 0.7MB | 텍스처 0.7MB, 버퍼 0MB, 캔버스 0개, 렌더 루프 0 |
| 최종 닫기 후 GC 힙 | 약 32.2MB | 32.2MB |

각 사이클 뒤 단일 뷰의 텍스처 수는 69개로 일정했고 브라우저/GPU 오류는 0이었다. 추정치는 요청한 GPU 크기를 추적한 값으로, 전체 브라우저 프로세스 메모리나 실제 GPU 상주 메모리와 같지 않다. 단일 뷰의 메모리를 획기적으로 줄였다는 기준에는 미달한다.

별도로 이전 배포와 복구를 같은 Edge/합성 단지에서 각각 2회 열기/닫기 후 측정했다. 브라우저 CDP가 제공한 해당 브라우저의 프로세스 ID에 대해 OS RSS를 합산했다. 단일 뷰 시작은 1203.9→1140.7MB, 두 뷰는 1235.7→1121.8MB, 모두 닫기는 1045.5→955.5MB였다. 프로세스 RSS에는 공유 페이지가 중복 포함될 수 있으며 GPU 드라이버·브라우저의 할당자 캐시도 남는다. 전체 브라우저 메모리가 작은 수준으로 줄었다고 판정할 수 없고, 최초 로딩 순간의 최대값을 측정한 자료도 아니다.

## 검증 자료와 남은 기준

- 단위/자원/GPU 회귀 테스트 16개, 부동산 회귀 테스트 12개 통과.
- 프로덕션 TypeScript/Vite 빌드 통과.
- 새 프로덕션 빌드를 로컬에서 제공하고 운영 API를 프록시하여 실제 단지 화면을 검사했다. 데스크톱과 모바일 화면 에뮬레이션에서 WebGPU high, 버튼 4개 미표시, 화면 드래그, 닫기/재열기, 브라우저 오류 0을 확인했다. 선택부터 표시는 각각 2197ms와 1663ms였다. 운영 서버에 새 코드를 배포한 검사가 아니며 실제 모바일 하드웨어 검증도 아니다.
- 수치 판정: `check-complex-targets.py`가 일반 조건 3회에서 첫 표시 1410ms(목표 ≤620.7ms), 최대 프레임 간격 132.4ms(목표 ≤20ms), 최대 입력 지연 127.9ms(목표 ≤20ms)를 확인하고 실패(exit 1)를 반환했다. WebGPU high 및 브라우저 오류 없음 항목만 통과했다.
- 측정 원본: `tmp/recovery-final-checks.json`, `tmp/recovery-comparison.json`, `tmp/complex-leak-recovery-shared/report.json`, `tmp/complex-paint-quality.json`, `tmp/complex-upload-quality.json`.
- 재현 명령: `python frontend/scripts/test-complex-performance.py --production --label <이름>`, `--cpu-rate 4 --paused-rail --stall-detail-seconds 5 --missing-feature-marker`, `--webgl`, `--fail-webgpu-pipeline`.
- 남은 기준: 전체 초기 로딩 3배, 로딩 중 지연 없는 입력/화면, 느린 CPU 및 WebGL에서 프레임 드랍 없음, 단일 뷰 메모리의 큰 폭 감소. 이 기준을 충족하기 전에는 최종 성능 목표 완료로 보고하지 않는다.

## 배포 상태

요청한 수치 판정이 실패하여 이번 수정은 재배포하지 않는다. 기능/빌드 통과를 성능 목표 통과와 혼동하지 않는다. 현재 운영 배포는 `647f48e`이며, 복구 변경과 재현 도구는 별도 개발 브랜치에서 보관한다.
