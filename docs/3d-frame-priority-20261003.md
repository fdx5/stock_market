# 3D 프레임 우선 개선 — 검증 미통과, 배포 보류

2026-10-03. 작업 브랜치: `fix/frame-budget-20261003`, 기반 커밋: `18d71c5`.
이 문서의 최초 검증 시점에는 운영 브랜치에 병합하거나 배포하지 않았다. **드랍 없음, 최초 로딩 3배, 메모리 개선 목표를 달성했다고 판정할 수 없다.**

이후 사용자가 미달 결과를 확인한 뒤 "배포후 드랍률 개선 결과만 보여줘"라고 명시적으로 요청했다. 이 요청에 따라 현재 검증한 수정본을 배포하고, 동일 실제 단지·브라우저·화면 크기로 배포 전후 각각 3회 측정한다. 이전 미달 판정을 통과로 바꾸지 않으며 실제 측정한 드랍률만 보고한다. 동시 작업 중인 루트 작업 디렉터리의 변경은 포함하지 않는다.

## 현재 변경

- 빌더 작업을 애니메이션 콜백 이후 프레임 예산 안에서 한 건씩 실행한다. 바쁜 프레임에 강제로 작업을 깨우던 타이머를 제거했다.
- WebGPU 경로에서 사용하지 않는 WebGL 반사·후처리·환경맵 리소스를 만들지 않는다.
- 셰이더 분석, 차량 형상, 보행 경로 계산, 준비된 텍스처의 디코딩을 워커로 옮겼다. GPU 바인딩 생성은 기존 디바이스에서 수행한다.
- 드로우 목록과 행 객체를 재사용한다. 차량 충돌 계산의 임시 배열을 제거하고 동일 경로 표본을 재사용한다.
- 보행자 관절 변환을 희소 행렬 계산으로 바꿨다. 인원, 관절 동작, 모델과 표시 거리를 줄이지 않았다.
- 같은 뷰의 렌더 패스 사이에서 변하지 않는 재질 값은 한 번만 직렬화한다. 조명과 패스별 리소스 바인딩은 계속 갱신한다.
- 달빛과 물결 4종의 기존 픽셀을 무손실 PNG로 저장했다. 실행 중에는 워커에서 디코딩하며, 파일을 얻지 못하면 기존 생성기로 복구한다. PNG 총 크기는 133,474바이트다.
- 닫힌 뷰의 늦은 워커 결과, ImageBitmap, 교체 중인 재질과 GPU 버퍼의 소유권 및 해제를 보강했다.

GPU 준비 완료 처리를 추가로 분산한 실험과 어댑터 탐색 워커는 로딩을 악화시켜 제거했다. CPU 캔버스로 바꾼 실험도 픽셀 차이가 발생해 제거했다.

## 검증 결과와 한계

관절 계산은 1만 가지 자세와 입력·출력 버퍼가 같은 경우에도 기존 GPU 업로드 Float32 값과 같다. 셰이더 워커 결과는 기존 셰이더 텍스트 및 접근하는 바인딩과 비교하는 별도 검사에서 통과했다.

달빛과 물결 4종의 준비된 PNG는 원래 캔버스 생성 결과와 픽셀 차이 0이다. 차량 형상·차량 표면도 기존 비교에서 차이 0이었다. 마지막 워커 디코딩 변경 후 건물 텍스처를 다시 검사했고, 50개 맵에서 최대 1/255 차이, 평균 0.00006143, 실행 오류 0으로 통과했다.

최종 제품 빌드(`npm run build`), Node 회귀 검사 27개 및 변경 내용의 공백 검사가 통과했다. **기능 검사 통과는 성능 목표 달성을 뜻하지 않는다.**

성능 판정은 로딩, 후속 준비, 카메라 이동, 거리 뷰, 단지 전환, 마우스 조작을 모두 포함한다. 고품질·고정 렌더 배율 1.5, 자체 건물 9개·이웃 건물 275개, Edge 155의 합성 장면이다. 실서비스의 모든 데이터와 장치 성능을 대표하지 않는다. 모든 프레임 간격이 20ms 이하여야 통과하며 기준을 완화하지 않았다. 캡처는 측정 후 수행한다.

최신 비추적 제품 빌드 측정 `prepared-effects-native`:

| 구간 | 20ms 초과 프레임 | 최장 간격 |
| --- | ---: | ---: |
| 최초 로딩 | 12 | 133.3ms |
| 후속 준비 | 5 | 50.1ms |
| 전체 뷰 | 1 | 33.2ms |
| 카메라 전환 | 1 | 49.3ms |
| 거리 뷰 | 0 | 18.5ms |
| 다른 방향 | 0 | 17.3ms |
| 단지 전환 로딩 | 8 | 166.7ms |

| 마우스 조작 | 0 | 17.0ms |

WebGPU·고품질 유지, 브라우저 오류 0. 로딩 중 입력 지연 최대 128.8ms. **전체 판정 실패.** 이전 실행은 정상 렌더 구간 모두 드랍 0이었지만 로딩·후속 준비·전환에서 실패했다. 실행 간 변동이 있어 반복되는 드랍 없음도 입증하지 못했다. CPU 4배 부하 검사 또한 통과하지 못했다.

추적 실행에서는 GPU 스레드의 238.5ms 작업과 긴 캔버스 작업이 관찰됐다. 이것만으로 모든 드랍 원인을 특정하거나, 준비된 PNG가 전체 성능을 개선했다고 주장할 수 없다. 준비된 PNG를 적용한 최종 실행도 위 표처럼 실패했다.

메모리 반복 열기 검사는 최초 808개 버퍼 대비 다시 열 때 855개로 원래 증가 허용 기준을 초과했다. 전부 닫으면 캔버스·WebGL 컨텍스트·뷰 애니메이션은 해제되고 GPU 텍스처도 대부분 해제되지만, 이 결과만으로 메모리 검사를 통과했다고 판정하지 않는다.

## 남은 필수 작업

1. 로딩과 전환 시 긴 GPU/브라우저 작업을 개별 리소스·파이프라인까지 대응시켜 원인을 제거한다.
2. CPU 부하 상태를 포함해 전체 구간 드랍 0을 반복 검증한다. 실제 사용자 데이터와 재현 환경에서도 확인한다.
3. 다시 열 때 증가하는 버퍼 47개 및 텍스처 2개의 할당 주체를 확인하고 메모리 검사를 통과한다.
4. 동일 환경의 이전 버전과 비교해 로딩 3배 및 메모리 목표를 별도로 입증한다.
5. 모든 요구사항의 검증이 통과한 변경만 운영 브랜치에 반영하고 배포한다.
