## 나무가 수풀·솜뭉치로 보였던 원인과 최종 선택

줄기 없는 카드 군집과 낮게 압축한 수관은 나무의 높이와 줄기를 지웠다. 이후 큰 불투명 수관 껍질은 솜뭉치처럼 보였고, 지나치게 적은 잎 묶음은 가지가 드러나는 성긴 나무가 됐다. 삼각형 수만 낮추는 기준이 품질 요구를 충족하지 못했다. 카드 군집, 40삼각형 각진 수관, 112~176삼각형 둥근 수관, 80잎 성긴 시제품은 최종 구현이 아니다.

최종 나무는 잎 모양의 얇은 닫힌 입체를 192개, 가지 묶음 48개에 배치한다. 잎마다 4삼각형, 줄기와 큰 가지 3개에 32삼각형을 사용하여 나무당 800삼각형이다. 직사각형 카드, 카메라를 향하는 회전, 알파 마스크, 거대한 구형 수관, 바람 애니메이션은 없다. 잎 표면에는 기존 CC0 식물 사진에서 미리 만든 작은 잎 무늬를 사용한다. 관목과 꽃의 구현은 나무와 별개이며 꽃잎의 알파 사용까지 제거했다는 뜻은 아니다.

느티나무·은행나무·소나무·벚나무·침엽수의 다섯 형상을 공유한다. 수종 원형 높이는 19/20/17/15/22m이고 산림은 개체 차이와 군집별 차이를 곱해 대략 11~28m 범위로 배치한다. 공원·가로수는 0.45배로 약 6~11m이며 기존 식재 위치를 보존한다. 줄기와 잎에 같은 변환을 적용하여 높이를 바꿔도 분리되지 않는다. 실제 지형 높이는 원래 식재 가능한 좌표에서 샘플링하며 군집의 평균 좌표를 사용하지 않는다.

산림 배치는 고정 10.5m 셀에서 원래 식재 좌표 하나를 선택하고, 64m 크기의 연속적인 군집 밀도에 따라 가장자리와 중심부의 분포를 달리한다. 가까운 숲보다 먼 숲의 식재 확률이 높다. 수종·높이·색상·군집은 월드 좌표 기반으로 고정되어 카메라 회전이나 로드 순서 때문에 바뀌지 않는다. 건물·도로·수면을 제외한 원래 식재 후보만 사용한다. 미분류 지형을 모두 산으로 덮는 방식은 아니다.

## 효율화 구조와 비용의 한계

잎 모델 5개와 공용 줄기 모델 1개를 근거리·원거리·공원 사이에서 공유한다. 사용자마다 잎 정점 배열을 복제하지 않고 `InstancedMesh`의 행렬과 잎 색상만 추가한다. 모델 생성은 수종 사이에 프레임 작업을 양보한다. 참조 수를 관리하여 한 군집이 닫혀도 다른 군집의 공유 버퍼를 해제하지 않고 마지막 소유자가 닫힐 때 한 번 해제한다. 자산 실패 시에도 같은 입체 나무로 대체하고 카드 나무로 돌아가지 않는다.

## 도로 높이·차선·가로등 공통 수정

도로 지형 평탄화가 큰 사각 영역의 산 높이를 도로로 읽어 평평한 도로를 46.04m까지 높이는 재현 자료가 있었다. 실제 연결 도로 폭 안을 샘플링하는 corridor grade와 높이 변화의 상·하한을 사용한다. 렌더링된 지형 삼각형 위에 도로를 드레이프하고 worker 또는 프레임을 양보하는 동일 결과의 대체 경로를 사용한다. 도로 밖 지형은 보존한다.

교차로 형상을 채운 아스팔트와 가로등 제외 검사를 함께 사용한다. 도로 중간 및 교차로 내부에는 가로등을 생성하지 않는다. 도로를 연결한 뒤 가구와 지형을 계산한다.

차선 오류의 원인은 짧은 도로 전체 생략, 범위를 벗어난 횡단보도·정지선, 굴곡에서 도로 폭보다 길어지는 정규화된 법선, 분할되지 않은 T자 교차로의 선, 홀수 차로의 누락된 구분선이었다. 차선은 실제 아스팔트 경계와 같은 보간 법선·꺾임 점을 사용하고 도로 끝 및 교차로 영역에 맞춰 자른다. 정지선 비활성 설정을 보존하고 짧은 도로와 마지막 부분 점선도 그린다. 도로 폭으로 차로 수를 추정하는 것은 명시적 차로 수가 없을 때만 한다.

실제 화면 검사에서는 도로 삼각형 중심점의 지형 매몰, 가로등 밑점의 차도 포함, 차선의 모든 정점·중심점이 아스팔트 밖인지 검사한다. 이 검사는 사진의 시각 평가와 함께 사용하며 전체 도로 데이터의 측량 정확도를 보증하는 것은 아니다.

## 회색 건물 면의 확인된 원인

결합된 아파트 모델에서 가장 넓은 수평면을 주 지붕으로 고르던 로직이 7~9m의 넓은 저층부 지붕을 선택했다. 그 결과 상부 아파트 면을 창문 벽 대신 코어 또는 띠로 분류해 회색으로 그렸다. 최고점에서 8m 이내의 상부 지붕을 선택하고 상부 지붕 증거가 없으면 창문 벽을 지우지 않게 수정했다. 사진과 기하 요청은 동일하며 면 분류만 바뀐다.

| 실제 결합 모델 | 이전 지붕 높이 → 수정 | 창문 벽 삼각형 면적 합 이전 → 수정 |
| --- | --- | --- |
| 루체하임 107·108 | 7 → 78m | 2,706 → 20,908 |
| 디에이치 814 | 9 → 114m | 13,755 → 109,098 |
| 디에이치 813 | 9 → 116m | 13,233 → 112,213 |

면적은 모델 삼각형의 합이며 중첩을 포함한다. 물리적인 등록 외벽 면적이 아니다. 정상 계단실의 회색 면은 보존한다. 복구한 창문 음영은 회색 단색 면보다 비용이 늘 수 있으므로 이 변경까지 GPU 비용 절감으로 분류하지 않는다. 반복 시간 변경 후 검은 표면 문제와 이 회색 면의 확인된 원인은 별개이며, 이번 수정만으로 모든 검은 깜빡임이 해결됐다고 주장하지 않는다.

## 지형과 기타 유지한 변경

근거리와 원거리 산림 분류에 지형 기복을 사용하여 미분류 언덕도 녹색·토양과 식생으로 표현한다. 잔디·꽃·토양을 단지 안 빈 공간에 배치하되 도로, 주차장, 물, 산업용 필지를 보존한다. 측량 정보가 없는 장식 꽃길을 실측 보행로라고 표시하지 않는다. 산림 꽃은 코스모스·데이지·코레옵시스·라벤더·수국·살비아의 6종이다. 나무를 꽃 군락의 빈 공간에도 강제로 덮지 않는다.

건물 기본 타일은 4×4 창문 반복과 1024×928 기반 재질로 변경했다. 원거리 차량은 비율·색상을 보존한 단순 메시를 사용한다. 열기구 높이는 20m 올렸다. 실제 사진 건물 기하는 유지한다. VWorld의 수백 요청을 하나로 합치는 서버/API 변경은 이번 작업에 포함되지 않았다.

## 검증과 수치 해석

최종 설정은 TypeScript/Vite production build, 건물·수목·WebGPU·도로 회귀 테스트, 부동산 UI 12개 테스트, 공원 지형·꽃·미분류 산지 재현 검사를 통과해야 배포한다. 동시 소유자의 모델 공유·마지막 해제, 원래 식재 위치, 지형 바닥, 닫힌 잎 형상, 수종 차이, 높이 분포, 원거리 밀도를 포함한다.

브라우저 QA는 Edge/WebGPU, 1440×900, pixelRatio 2, 고품질, 낮 12시, 실제 API를 사용한다. `fps`와 `gpuMs`는 특정 시점 표본이며 동일 장치의 교차 반복 비교 없이는 3배 개선 등의 인과적 수치로 표현하지 않는다. pointer→다음 animation frame 지표는 입력 후 다음 프레임 콜백까지의 근사치이며 실제 화면 픽셀 갱신 지연 측정과는 다르다. 로딩 중 long task와 33ms 초과 프레임을 함께 기록한다. QA 자체의 공간 검사·스크린샷 비용도 포함될 수 있으므로 완료 후 최대 프레임 간격만으로 제품 프레임 드랍을 단정하지 않는다.

**전체 요소 3초 로딩, 프레임 드랍 0, 전체 삼각형 1/20 목표는 달성으로 보고하지 않는다.** 앞선 10.5m 최종 밀도 적용 전 측정에서 강남데시앙포레는 전체 조경 약 49초, WebGPU 60 FPS, GPU 약 5.9ms였고 로딩 중 긴 작업이 남았다. 최종 수치는 별도 검증 JSON과 아래 측정 표를 참조한다.

## 전체 로딩 경로 개선과 외부 지리정보

전체 완료 목표는 사용자 지정 7초다. 선택 시각부터 단지·주변 건물 실측 모델, 도로·교통, 근거리·원거리 식생, 수면·보행자·주변 인물이 완료되고 실제 WebGPU 준비 상태가 참인 첫 프레임까지 측정한다. 단순히 조경 완료 표시를 빨리 바꾸는 방식으로 측정하지 않는다. 화면 dataset의 GPU 상태는 주기적으로 갱신되므로 QA는 실제 렌더러의 ready/pending/compiling/failed/starved를 직접 확인한다. 숲이 없는 지역도 원거리 지면과 꽃·잔디 작업이 끝나야 완료다.

조경 생성은 고정 개체 수마다 한 프레임을 무조건 기다리던 방식에서 실제 CPU 3ms마다 양보하도록 변경했다. 작은 작업의 admission 한도는 12ms이며, 대기 후 실행 구간은 3ms로 제한한다. 다른 장면 작업의 기본 admission 9ms는 유지한다. 꽃·관목 worker 병합, 잔디 기하, 공원 나무, 산림 나무를 동시에 시작하고, 외부 지리정보·주변 건물·교통도 첫 프레임과 병행한다. 주변 보행자는 최종 숲을 기다리지 않는다. compact 모드에서 중간 측량 조경 복사본은 생략하고, 모든 식재 좌표·종류가 정확히 같은 마지막 조경은 기존 GPU 자원을 재사용한다. 물 정보가 달라지면 실제 수면 마스킹 결과를 적용하여 다시 생성한다.

CPU 프로파일에서 식물 처리 루프의 URL 렌더링 모드 확인에 약 609ms가 쓰인 사례를 찾았다. 검색 문자열이 달라질 때만 모드를 계산하고 Forest/plantForest 작업 동안 결과를 보관한다. 이미 공용 입체 나무로 대체한 옛 나무 생성 루프는 compact 모드에서 실행하지 않는다. 공유 기하 외에도 잎 재질과 줄기 재질 두 개를 모델 은행에서 공유하여 군집마다 네이티브 재질과 셰이더를 중복 준비하지 않는다.

운영 water 조회가 약 41,422ms 걸리고 source가 null인 사례가 있었다. 기존 Overpass 미러를 순차적으로 20초씩 기다리고 오류의 빈 결과를 하루 캐시하던 경로가 원인이었다. geography 조회에만 총 예산 4초와 짧은 transport timeout을 적용했다. 기존 건물 조회의 기본 timeout은 변경하지 않는다. requests의 read timeout은 바이트마다 재설정될 수 있으므로 모든 네트워크 상황에서 엄밀한 4초 상한이라고 주장하지 않는다.

검증된 지리정보는 기존 realestate_store의 영속 facts 저장소에 저장한다. 결과가 있는 조회는 30일, 검증된 빈 조회는 24시간 유지하며 동일 중심·종류·반경 조회는 한 번만 실행한다. 중심 좌표는 소수점 네 자리로 구분한다. 실패 결과는 영속 빈 결과로 저장하지 않고, 90일 이내 마지막 검증 결과가 있으면 보존한다. 검증 결과가 없으면 짧은 재시도를 허용한다. API는 upstream 오류에 no-store를 반환하고 새 프런트엔드의 v=2 URL로 기존 잘못된 브라우저 빈 캐시를 피한다. 외부 조회 실패 시 새로 발견하지 못한 지리정보까지 모두 그렸다고 보장하지 않는다.

로컬 QA는 운영 건물·필지 API와 실제 변경된 로컬 geography 백엔드(실제 OSM 조회 및 SQLite 영속 캐시)를 사용한다. 응답을 가짜로 고정하거나 물과 나무를 지워서 로딩 시간을 맞추지 않는다. 운영 배포 후에는 운영 백엔드를 대상으로 동일 검증을 실행한다. CPU 프로파일링과 다른 3D 화면은 최종 시간 측정 중 실행하지 않는다.

스케줄러는 한 프레임에 한 continuation만 허용하던 제한을 없앴다. MessageChannel 작업 사이에 실제 소비 시간을 다시 검사하며 FIFO를 유지한다. admission 예산이 소진되면 다음 프레임으로 넘어가고, 계속 바쁜 화면에서는 100ms마다 하나씩 허용하는 기존 기아 방지 규칙을 유지한다. 숨겨진 탭도 프레임을 기다리지 않고 완료한다. 이 세 동작은 모의 프레임과 실제 소모 시간으로 회귀 테스트한다.

추가 backend pytest 13개는 영속 빈 조회, 실패 비저장, 호수의 stale 보존, 동시 단일 요청, 중심·반경 분리, geography 예산과 기존 건물 timeout 보존을 포함한다. 수목·도로·WebGPU 회귀 51개, 스케줄러 3개와 부동산 UI 12개도 별도로 실행했다.

6. 같은 모델·시점·카메라로 cold/warm 교차 반복, CPU 부하 통제, 입력 p95/p99, GPU main/shadow/plant 패스와 다운로드를 함께 비교한다. 나무 수를 무작정 줄이는 최적화는 품질 퇴보로 판단한다.

## 최종 측정 및 배포 기록

### 도로의 건물 침범 원인과 보완

도로 조회는 반경 600m까지였지만 기존 경계 검사는 선택 단지 및 가까운 문맥 건물만 사용했다. 뒤늦게 생성되는 외곽 건물은 보호되지 않았다. 도로에 걸리는 건물을 제외하는 이전 처리도 제거했다. 자료 불일치를 실제 건물을 지우는 방식으로 해결하지 않는다.

도로 영역보다 80m 넓은 영역의 지상 건물 외곽선을 마지막 페이지까지 읽는다. 1,000건 미만인 응답은 추가 페이지를 요청하지 않는다. 짧은 도로 응답에 4번 반복하던 조회는 1번으로 줄였다. 이천의 넓은 경계 조회는 3,187건/4페이지였고, 이전 화면 반경의 2,403건 중 가까운 문맥 437건만 검사하던 범위를 보완했다. 과밀 지역에서 필요한 추가 페이지의 비용은 남아 있다.

건물 경계와 원본 중심선을 이동하지 않는다. 등록 폭이 건물 간격보다 넓을 때만 차로 폭을 유지 가능한 범위에서 줄이고, 중심선이 건물을 통과하면 불가능한 구간만 제외한다. 임의 우회로나 연결 직선을 만들지 않는다. 렌더링 직전 도로·차선·보도 메시를 건물 외곽선과 정확히 차집합 처리해 교차로 확장 면도 보호한다. 보도는 실제 도로 면에서도 제외한다. UV·색상·법선을 보간하여 유지하며 경계만 접하면 기존 인덱스 및 버퍼를 유지한다. 계산은 작업자에서 수행한다.

지상 층수 0, 지하 층수 양수, 지상 높이 없는 지하철역 자료를 가상의 2층 지상 건물로 생성하던 처리도 막았다. 지상 층수가 미상인 일반 건물을 함께 지우지 않는다.

실제 로컬 WebGPU 장면의 도로 삼각형 합집합과 VWorld 지상 건물 외곽선을 교차 검사한 결과:

| 사례 | 비교 건물 외곽선 | 실제 도로 삼각형 | 건물과 겹침 |
| --- | ---: | ---: | ---: |
| 설봉1차푸르지오 | 3,059 | 75,385 | 0건, 0㎡ |
| 루체하임·우성7·영희초등학교 주변 | 1,455 | 94,584 | 0건, 0㎡ |

해당 조회 자료와 장면의 검사 결과이며 전국 원본 측량 데이터의 정확성을 보증하지 않는다. 지상/고가 레벨 정보가 없는 입력의 입체 교차는 별도 검증이 필요하다. VWorld 실사 모델이 등록 외곽선보다 돌출된 경우도 별도 검증 대상이다.

### 차선과 차량 바퀴의 비용

차선이 DEM으로만 높이를 정해 실제 도로 아래에 묻히는 오류를 확인했다. 수정 전 루체하임 48,896개 차선 삼각형 중 141개가 최대 0.175m 묻혔다. 실제 아스팔트 삼각형과의 교차점에서 필요한 최소 높이만큼 기존 차선 삼각형을 들어 올린다. 삼각형 수나 draw call을 늘리지 않는다. 차량 접지 높이도 실제 아스팔트 면에서 구한다.

가까운 차량의 원본 바퀴 부분만 분리하고 모든 차량이 두 개의 공통 인스턴스 메시를 공유한다. 전체 타이어·휠은 692삼각형/91,344바이트, 기존 타이어용 휠 덧씌움은 428삼각형/56,496바이트의 공유 소스 버퍼다. 불투명 깊이 기록, 닫힌 휠 뒤판, 밝은 5개 스포크와 측면 링으로 도로 비침을 막고 회전을 식별하도록 했다. 실제 이동거리/반지름으로 회전하며 정지 시 멈추고 후진 시 반대로 돈다. 원거리에는 상세 바퀴를 추가하지 않는다. 기존 정지 바퀴보다 삼각형 비용은 증가한다.

실제 확대 검사에서 0.33m 이동 시 바퀴 행렬이 변하고 정지 시 동일하게 유지됐다. 브라우저 오류는 없었다. 교차로 이동은 회전 자세를 포함한 연속 SAT 검사를 적용하며 우선권으로 물리적 충돌 검사를 우회하지 않는다. 같은 프레임의 교차로 진입·출구 차로 예약을 공유한다. 좁은 단일 차로에 가상의 양방향 차로를 추가하지 않는다. 장시간 혼잡은 별도 검증 대상으로 남긴다.

### 문산읍의 도로 누락

파주한양수자인리버팰리스는 VWorld 도로중심선 조회가 단지 주변과 반경 600m 모두 `NOT_FOUND`/0건이었다. 건물 조회는 정상이다. 렌더러가 받아 놓은 도로를 숨긴 문제가 아니다. 이 배포는 빈 응답에 임의 도로를 생성하지 않으며, 다른 도로 자료로 보완하는 대체 경로는 아직 구현하지 않았다.

### 검사와 남은 목표

프런트 회귀 검사 84개, 지리 캐시·건물 백엔드 pytest 13개, TypeScript/Vite production 빌드가 통과했다. `audit-3d-landscape.py`는 실제 전체 완료·네이티브 준비·지형 매몰·차선 경계·가로등 도로 침범을 검사한다. `audit-traffic-junction.py`는 실제 차량 이동 함수로 360초를 전진하며 프레임마다 차량 교차 여부를 검사한다. 실행은 저장소 루트에서 하며 원자료는 로컬 `tmp`에 보존한다.

최근 캡처 선택~차량 준비는 설봉 약 11.32초, 루체하임 약 10.73초였다. 이전 5개 사례 전체 완료는 약 6.8~9.7초였다. 화면 전체 **7초 목표는 아직 달성했다고 판단할 수 없다.** 넓은 경계 조회와 정확한 표면 검사가 추가돼 기존 타이밍을 이번 배포의 개선 배율로 사용하지 않는다. 60FPS 표시도 로딩 중 드랍 0의 보증이 아니다.

소스·자산 commit을 만든 뒤 새 수목 자산만 해당 commit으로 CDN에 고정한다. 환경 오버라이드 없는 production 빌드를 검사해 main에 fast-forward하고 `/api/health` commit과 실제 운영 장면을 확인한다. 키가 포함된 요청 URL과 원본 API 응답은 저장소에 커밋하지 않는다.

배포 콘텐츠 commit은 `480e72b856f5f2f7597fcea1d0b4afde9e6d3af1`이다. 새 수목 자산 5개만 이 버전에 고정하고 기존 대용량 차량·이미지는 이전 CDN pin을 유지한다. CDN 경로 검사 2개 추가로 최종 프런트 검사는 86개다.

최종 실제 루체하임 360초 시뮬레이션: 차량 462대, 프레임 전체 차량 겹침 0회, 신호 제어 교차로 25개, 신호 헤드 90개, 위치가 바뀐 차량 461대, 80초 넘는 장기 대기 차량 141대였다. 따라서 충돌 방지는 확인했지만 교차로 장기 정체 문제가 모두 해결됐다고 주장하지 않는다. 최근 데시앙 실제 모든 요소·네이티브 준비 완료는 선택 후 10.3646초였고, 지형에 묻힌 도로 0개, 도로 밖 차선 정점 0개, 차도 안 가로등 0개, 브라우저 오류 0개였다. 이번 배포에서 7초 목표는 미달성이다.
