# iPad Safari 3D 렌더링 부하 개선 — 2026-10-04

## 사용자 증상과 범위

사용자는 iPad Safari에서 약 10 FPS, 일부 장면 전환에서 흰 화면을 보고했다. 물리 iPad 모델은 아직 확인되지 않았다. 데스크톱에서 터치·MacIntel·deviceMemory 미제공 조건을 재현했고 Windows Playwright WebKit으로 기능을 검사했다. **실제 iPad의 최종 FPS나 OS 메모리 종료를 측정한 결과는 아니다.**

## 확인한 병목

- 이전 수목은 먼 산에서도 나무당 잎 192개(잎 768 + 줄기/가지 32 = 800 삼각형)를 그렸다. 인스턴싱은 소스 버퍼와 CPU 복사를 줄이지만 인스턴스마다 GPU에서 처리하는 삼각형 수까지 없애지는 않는다.
- 해상도 조절은 WebGPU에 여유가 있을 때 올리는 기능만 있었다. Safari WebGL의 느린 프레임에는 대응하지 않았다.
- 첫 크기 설정에서 `max(dpr, ...)`가 시작 픽셀 예산보다 높은 해상도를 강제했다. 메모리 상한에서 잘렸지만 성능을 위한 시작 예산은 지켜지지 않았다.

## 적용 방식

1. Apple 터치 장치(iPad의 데스크톱 Mac UA 포함)와 보고된 메모리 4GB 이하 장치에 공통 예산을 적용한다. 화면 이동, 외부 마우스, 전체 화면, `pr` 디버그 파라미터에도 메모리 상한이 우선한다.
2. 단지 원점에서 250m 이내 수목은 잎 192개를 유지한다. 250–500m는 96개/416 삼각형, 500m 이상은 48개/224 삼각형이다. 먼 개체의 잎 크기 보정은 최대 1.5배로 제한했다. 나무 위치·개수·높이·수종·색상과 줄기/가지 형태를 유지하며 카드나 빌보드를 도입하지 않았다.
3. 5종 × 거리 단계의 작은 지오메트리 은행을 조경 그룹끼리 공유한다. 카메라 이동마다 나무를 다시 생성하지 않는다. 이 방식의 거리는 카메라가 아닌 단지 원점 기준이다. 멀리 있는 산으로 크게 확대하면 잎 디테일이 가까운 단계보다 적다는 한계가 있다.
4. 제한 장치의 시작 화면 예산은 125만 픽셀, 메모리 상한은 200만 픽셀이다. 느린 프레임이 1.5초 이상 지속되면 렌더 비율을 15%씩 낮추며 CSS 픽셀당 0.7배까지 허용한다. 일반적인 큰 화면에서도 절대 픽셀 상한이 우선한다. 3초 재조절 대기와, 충분한 여유가 8초 이상 지속될 때 5%씩 복원하는 규칙으로 진동을 막는다.
5. 로딩·새 장면 준비·백그라운드·큰 단발성 멈춤은 해상도 판단에서 제외한다. 디버그 `pr`는 고정 측정용으로 자동 조절을 끄되 메모리 상한은 유지한다. 건물 지오메트리나 차선·도로·조경 개체를 FPS 조절 과정에서 삭제하지 않는다. 부하 시 화면 선명도가 낮아지는 비용은 있다.
6. 그림자 1024, WebGL MSAA 0, WebGPU low 정책, paint 긴 변 768, 이전 단지 동시 보관 중지 및 원자적 버퍼 크기 변경은 [검은 건물/메모리 조사 기록](3d-black-facade-investigation-2026-10-04.md)에 함께 기록한다.

## 비교 측정과 해석

강남데시앙포레, CSS viewport 1024×1366, DPR 2, iPad navigator profile, Edge WebGL, RTX 3070에서 프레임당 실제 WebGL 호출을 계수했다. 삼각형은 본 장면 외에 그림자·후처리 패스를 포함하므로 화면에 보이는 고유 삼각형과 다르다. GPU readback은 넣지 않았다.

| 항목 | Safari 메모리 제한만 적용한 중간 버전 | 추가 FPS 개선 적용 |
| --- | ---: | ---: |
| 프레임당 삼각형 처리 | 약 13,200,551 | 약 7,294,852 |
| 그리기 호출/프레임 | 약 263 | 약 272 |
| 렌더 픽셀 | 1,755,572 | 1,247,988 |
| 렌더 비율 | 1.24 | 1.05 |
| 데스크톱 GPU 프레임 속도 | 약 60 FPS | 약 60 FPS |

삼각형 처리는 약 44.7%, 픽셀은 약 28.9% 감소했다. 거리별 배치로 호출은 약 3.5% 증가했다. GPU 소스 은행에 저해상도 모델을 추가하는 작은 버퍼 비용과 교환한 결과다. 두 버전 모두 데스크톱에서 60 FPS 상한에 도달하므로 이를 iPad FPS 증가율로 환산하지 않는다. 빌드가 동시에 실행되던 첫 측정의 14 FPS는 비교 결과에서 제외했다.

기록: `tmp/ipad-fps-before-idle.json`, `tmp/ipad-fps-after.json` 및 PNG. 이 비교는 자동 회전 중 계수한 것으로 카메라 각도가 완전히 같지는 않다. 정밀한 GPU 시간 비교에는 다음 명령의 고정 시작 시점 측정을 사용한다.

추가 기능 검증: 회귀 검사 48개 통과. WebKit 단지 전환 3회, 가로/세로 변경 및 WebGL context loss/restore 후 모델 재생성 통과, JavaScript 오류 0건. 캔버스 크기 setter까지 감시해 전환 중 최대 약 199.9만 픽셀을 확인했다. 고정 시작 카메라에서 느린 프레임을 주입했을 때 약 10.4 FPS 조건에서 비율 1.05→0.70으로 내려갔고, 주입을 해제하면 0.73으로 점진 복원됐다. **주입 시험의 10.4 FPS는 강제 지연이므로 실제 GPU의 개선 전후 FPS 비교가 아니다.** 기록은 `tmp/ipad-fps-pressure.json`, `tmp/ipad-final-safari.json`에 남겼다.

최종 통합에서는 원격 `585db54`의 차량 재시작 수정도 보존했다. 해당 차량 테스트를 포함한 **52개 검사 통과**. 최신 iPad profile WebGPU에서 신일1 단지·시각 변경과 같은 버전의 다른 재질 객체 교체를 검증했고, 살아 있는 GPU 재질·텍스처 binding을 유지했다. 렌더 픽셀 1,250,225, facade paint 최대 긴 변 768, 조경 complete 및 오류 0건이었다(`tmp/ipad-final-native.json`).

## 다음 개선 시 주의점

- 빌드나 여러 브라우저 검사를 동시에 돌린 FPS를 성능 비교로 쓰지 않는다. 같은 카메라, 시각, viewport와 캐시 조건을 맞춘다.
- 인스턴싱의 CPU/버퍼 절감과 GPU 삼각형 감소를 구분한다. 모든 잎 모델을 고정 비용이라고 판단하지 않는다.
- 물리 iPad에서 단지 전환, 회전·확대, 가로/세로 전환을 측정해야 최종 FPS 목표 달성 여부를 판단할 수 있다. 현재 30 FPS는 제어 목표이며 보장 결과가 아니다.
- 낮은 해상도에서도 약 10 FPS가 지속되면 화면 픽셀보다 CPU 애니메이션 또는 버텍스 부하를 먼저 분리 측정한다. 나무 삭제나 건물 재질 단순화로 증상을 숨기지 않는다.
- 장기적으로 화면상 크기 또는 카메라 거리 기준의 수목 단계와 공간별 인스턴스 컬링을 검토한다. 호출 증가·전환 시 팝핑·버퍼 재할당·근접 나무 품질을 함께 측정해야 한다.
