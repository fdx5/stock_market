# 입력 없는 소셜 로그인과 개인화 서비스 설계

현재 요청은 기능 가능 여부 및 데이터 보호 조건 정리다. 소셜 로그인 기능은 아직
구현·활성화하지 않았다. 기존 테마/Toss/1면 수정 배포와 별도의 작업으로 진행한다.

## 사용 흐름

Google 또는 네이버 로그인 버튼 → 로그인 제공자에서 인증 → 서버에서 응답 검증 →
내부 회원 생성 또는 조회 → 내 관심종목/분석 보고서 화면.

이름·이메일·전화번호·사진·닉네임·비밀번호 등을 직접 입력하는 회원가입 화면은 없다.
동일 사용자 구분에는 제공자 식별값과 내부 회원 키가 필요하므로 '저장 정보가 전혀 없다'는
표현은 사용하지 않는다. 식별 키와 관심종목/보고서도 계정에 연결되는 가명 데이터로 보호한다.

## 저장 구조

| 용도 | 최소 저장 구조 |
| --- | --- |
| 회원 | 난수 `user_id`, 가입 시각, 상태 |
| 외부 계정 연결 | `user_id`, 제공자 종류, 제공자 식별값의 키 기반 HMAC |
| 세션 | 세션 토큰의 해시, `user_id`, 만료 시각 |
| 관심종목 | `user_id`, 암호화된 종목/메모/순서, 추가 시각 |
| 개인 설정 | `user_id`, 암호화된 설정 내용 |
| 분석 보고서 | 난수 report ID, `user_id`, 암호화된 보고서/대상 종목/기준 시각 |

계정 연결용 HMAC은 SHA 해시처럼 공개적으로 재현할 수 있는 단순 해시보다 서버의
별도 비밀키를 사용한다. 회원에 연결되는 업무 내용은 AES-GCM 등으로 암호화하고,
nonce/암호문/인증 태그를 관리한다. 검색에 필요한 경우 별도 키 기반 검색 인덱스를
최소한으로 두며 원문을 중복 저장하지 않는다. 난독화는 암호화를 대체하지 않는다.

현재 서비스의 FastAPI·React 및 Turso/libSQL 구조를 확장할 수 있다. 기존 관리자
로그인은 단일 관리자용이므로 회원 로그인과 세션을 별도로 만든다. 현재 관심종목 UI는
제거된 상태이며 예전 localStorage 데이터는 남겨 두었으므로, 이를 자동으로 서버에
전송하지 않고 사용자가 명시적으로 관심종목을 추가하는 흐름을 만든다.

이메일을 저장하지 않으므로 서로 다른 Google·네이버 계정을 이메일로 자동 병합하지
않는다. 두 로그인 수단을 같은 회원으로 연결하려면 로그인된 상태에서 양쪽 인증을 완료하는
명시적인 계정 연결 기능을 사용한다.

## 전용 화면

- **내 관심종목**: 국내/해외 종목 추가, 묶음 보기, 시세/지표/최신 분석 상태.
- **내 분석 보고서**: 관심종목별 보고서, 생성 시점별 이력, 보고서 상세.
- **내 설정**: 로그인 수단 연결 및 개인화 설정. 프로필 정보 입력은 없다.

공통 종목 분석은 기존 분석 데이터를 재사용하고 회원별 목록/보고서 연결만 분리해
동일 종목 분석을 회원마다 중복 생성하지 않도록 설계한다. 로그인 유지 쿠키는
HttpOnly/Secure/SameSite로 설정하고, 사용자별 권한은 서버에서 검증한다.

## 실제 연동을 위한 준비

- Google Cloud OAuth 앱 등록, 클라이언트 설정, `kospimap.com` 콜백 URL 등록.
- 네이버 개발자 앱 등록, 최소 제공 정보 설정, 콜백 URL 등록, 공개 서비스 검수.
- 제공자 비밀키와 암호화/HMAC 키는 배포 서버의 비밀 설정에 저장한다.
- AI에는 운영 DB 읽기 전용 권한만 제공한다. 현재 전체 DB 자격 증명 접근을
  실제로 분리하지 않은 상태에서 삭제가 기술적으로 불가능하다고 단정하지 않는다.

AI 데이터 보호 지침은 [AGENTS.md](../AGENTS.md)에 기록했다.
