# 3D 도로 중앙선·차선 누락 수정 — 2026-10-04

## 문제와 원인

운영 의정부롯데캐슬골드포레(가능동 860)에서 아스팔트는 렌더링됐지만 중앙선과 차선이 없는 구간을 재현했다. 데이터 어댑터는 공급자 `rdln` 값이 없으면 차로 수를 1로 저장한다. 기존 `buildRoadMarkings`는 `lanes < 2`인 도로를 통째로 건너뛰었다. 따라서 폭 8~14m인 도로도 차로 메타데이터 누락만으로 중앙선, 차로선, 외측선이 모두 사라졌다. 폭 7m 미만 도로의 외측선을 생략하는 별도 조건도 있었다.

수정 전 실제 장면은 도로 53개, 교차로 내부 조각 9개, 선 생성 계획 33개였다. 교차로가 아닌 11개 구간이 계획에서 누락됐다. 폭 약 14.23m, 길이 약 359m인 구간도 포함됐다. 이전 검증은 생성된 선이 아스팔트를 벗어나지 않는지 확인했으나, 도로 전체에 필요한 선이 생성됐는지 역으로 확인하지 못했다.

추가 공통 검사에서는 신동아파밀리에의 급한 굴곡 3곳에서 얇은 선의 실제 메시가 수 mm 끊어진 것도 발견했다. 중심 도로의 법선을 평행 이동한 차선 리본에 그대로 사용하면 짧은 굴곡에서 사각형이 접힌다. 지형에 맞추기 전 원본 메시에서도 동일한 빈틈이 재현됐다.

## 공통 수정

- `roadLanes.ts`의 `roadLaneCount`를 도로선과 차량 경로에 공통 적용한다. 등록 차로 수가 2 이상이면 유지한다. 차로 수가 없거나 1이고 도로 폭이 5.6m 이상이면 폭/3.5m로 추정하며 최소 2차로를 사용한다. 공급자가 주는 1이 실제 단일 차로인지 누락 기본값인지 구분되지 않으므로, 이 값은 실측 차로 수라는 의미가 아니다. 현재 장면의 양방향 차량 모델에 맞춘 시각적 복구 정책이다.
- 좁은 단일 차로에는 노란 중앙선을 임의로 추가하지 않고 폭 2.4m 이상이면 흰 외측선을 생성한다. 다차로에는 중앙선과 내부 점선을 생성한다. 교차로 내부 제외와 기존 정지선·횡단보도 규칙은 유지한다.
- 도로 합치기 및 교차로 분할을 완료한 뒤 차량 경로의 차로 수만 정규화한다. 합치기 전에 차로 수를 바꿔 도로 중심선이나 폭이 달라지는 일을 피한다.
- 폭 0.2m 이하의 얇은 선은 자신의 경로 접선으로 사각형을 만들고, 굴곡의 연결부를 작은 삼각형으로 채운다. 면적 0인 연결 삼각형은 생성하지 않는다. 넓은 횡단보도·정지선은 기존 도로 법선 규칙을 사용한다.

## 실제 렌더링 검사

로컬 빌드 + 운영 건물/도로 데이터, Edge WebGPU의 실제 활성 메시를 수집했다. 지형 보정 및 건물 마스킹까지 적용된 아스팔트 위에서 중앙선, 흰 외측선, 점선의 유효 부분을 1m 간격으로 검사한다. 이중 중앙선은 양쪽을 모두 검사한다. 점선의 의도된 빈 구간, 교차로 내부, 실제 아스팔트가 없는 마스킹 구간은 검사 대상에서 제외한다. 검사 지점에 선 메시가 존재하며 아스팔트보다 1mm 이상 위에 있어야 통과한다.

| 장면 | 도로 / 교차로 내부 | 선 생성 계획 | 실제 선 검사 지점 | 누락·묻힘 |
| --- | ---: | ---: | ---: | ---: |
| 의정부롯데캐슬골드포레 | 53 / 9 | 44 | 25,320 | 0 |
| 신동아파밀리에 | 143 / 13 | 130 | 42,567 | 0 |
| 래미안 개포 루체하임 | 75 / 0 | 75 | 43,733 | 0 |

의정부롯데캐슬골드포레의 수정 전후 도로 중심 좌표와 폭은 53개 모두 동일했다. 위에서 내려다본 스크린샷에서도 누락됐던 선을 확인했다. 검사 지점의 통과는 전국 모든 원본 도로의 정확성이나 연속적인 모든 좌표를 보증하지 않는다. 새로운 제보 위치는 같은 검사에 추가해야 한다.

## 자원 비용과 성능 해석

의정부롯데캐슬골드포레의 실제 도로선 메시 측정:

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 도로선 메시 수 | 2 | 2 |
| 선 삼각형 | 25,199 | 36,086 |
| position 버퍼 바이트 | 907,164 | 1,299,096 |

누락된 11개 구간의 선과 굴곡 연결부를 복구하므로 선 자체의 삼각형은 10,887개, position 버퍼는 391,932바이트 증가한다. 이는 전체 GPU 메모리 증가량이 아니라 해당 속성만 측정한 수치다. 도로별 별도 메시나 외부 텍스처, 새 데이터 요청은 추가하지 않았다. 선은 기존 노란색/흰색 2개 메시로 합쳐서 제출한다. 성능을 이유로 필요한 선을 생략하지 않는다.

로컬 데스크톱에서 제보 장면 완성 후 표시 FPS는 약 60이었다. 동시 빌드·브라우저 실행 및 네트워크 변동이 있어 FPS 개선 비교 자료로 사용하지 않는다. 물리 iPad Safari의 FPS나 전체 조경 7초 완료를 이번 검사로 달성했다고 주장하지 않는다.

## 반복 검증

저장소 루트에서 실행한다. Playwright/Edge가 필요하다.

```powershell
python frontend/scripts/audit-road-markings.py --url "검사할 3D 지도 URL" --out tmp/road-lines-case
python frontend/scripts/check-road-markings.py tmp/road-lines-case.json
```

수집기는 도로, 교차로 제외 정보, 실제 아스팔트·선 geometry, 렌더러 준비 상태, 화면 스크린샷을 저장한다. 공급자 요청 URL이나 API 키는 기록하지 않는다. 검사기는 도로별 선 생성 계획 누락, 선 메시 누락, 도로 아래 묻힘, 페이지 오류를 실패로 처리한다. 결과는 `*-coverage.json`에 저장한다. 원본 메시와 스크린샷은 `tmp/road-lines-{ganeung,shindonga,luceheim}-verified*`에 보관한다.

`test-road-continuity.mjs`에 누락 차로 기본값, 좁은 단일 차로, 추정 차로의 교차로 제외, 실데이터 급굴곡의 리본 접힘 재현을 추가했다. 선이 아스팔트 밖으로 나가지 않는 기존 검사와 함께 실행해야 한다. 미래 최적화에서도 **선이 도로 안에 있는지**와 **각 도로에 필요한 선이 있는지**를 별도로 확인해야 한다.

최신 운영 커밋 `276a015`를 먼저 반영하고 도로·건물 간섭, 교차로 차량, 휠 충돌, 기기 예산, 프레임 분할, 재질 수명, 주행 경로 인계 관련 자동 검사까지 75개가 통과했다. TypeScript 검사 및 운영 설정 빌드도 통과했다.

기존 건물/도로 간섭 방어의 회귀 검사도 수행했다. 신동아파밀리에 장면의 실제 건물 표면 25개와 렌더링된 아스팔트 면을 비교한 결과, 0.01㎡를 넘는 도로 침범은 0건이었다(`tmp/road-lines-guard-shindonga-*`).
