## 변경과 확인된 부담 증가

문제가 된 산림 변경은 수관 폭을 두 축에 함께 곱했다. 원래 식재 간격에서 수관의 수평 면적이
최대 약 2.54배 커질 수 있었다. 삼각형 수와 메모리가 같아도 겹치는 잎의 화면 비용과 경계 구가
커질 수 있으므로, 기존의 버퍼 예산 검사만으로 성능을 통과시킨 판단은 충분하지 않았다.
다만 이 배율이 실제 GPU 시간의 배율이라는 뜻은 아니며, 사용자 환경의 심각한 초기 멈춤을
이 항목 하나로 재현·확정한 것은 아니다.

로컬 변경은 다음과 같다.

- 수관 두 축을 서로 반대로 조절해 기존 수평 면적을 유지한다. 다섯 군집의 수종 혼합,
  높이·방향·기울기와 넓어진 위치 흔들림은 유지한다.
- 군집별 추가 밀도 감소를 제거했다. 성능을 얻기 위해 식재 밀도, 근거리 192개 잎,
  기존 LOD, 그림자 해상도, 렌더링 해상도를 낮추지 않았다.
- 고정 지형·건물·식재의 반복 행렬 합성을 줄이고, 소유한 네이티브 객체의 월드 경계 구를
  정확한 변환 버전과 경계 변경 검사로 재사용한다.
- 한 객체의 카메라 컬링 변화가 큰 렌더 번들 전체를 다시 기록하지 않도록 객체별로 캐시한다.
  GPU 입력·인덱스·범위 변경을 모두 검사하고 그리기 순서를 유지한다.
- 반복되는 도로 타이어 높이 조회와 정지 차량의 동일 경로 판정, 불변 도로의 연결 후보와
  방향·경사 계산을 재사용한다. 차량의 시간 간격, 이동 속도, 충돌 규칙은 유지한다.
- 차량의 전체 예상 경로와 떨어진 충돌 후보 및 화면에서 완전히 벗어난 도로의 차량 행렬 작업을
  먼저 배제한다. 기존 정밀 판정과 차량 업데이트·난수 순서는 유지한다. 타이어 높이의 삼각형 경계 검사도 추가했다.
- 고정 객체의 동일한 GPU draw uniform을 다시 포장하지 않고, 변경된 슬롯 범위만 업로드한다.
  움직인 다음 프레임의 이전 행렬, 속도 초기화, 파라미터 변경, 버퍼 성장·슬롯 재사용을 검증했다.

작은 산림 컬링 셀, 깊이 선행 렌더링, GPU 작업 분할, 차량/그림자 작업의 프레임 위치 변경은
성능 이득이 없거나 나빠져 최종 코드에서 제외했다.

## 실제 크롬 측정

Chrome 154, RTX 3070(WebGPU `nvidia/ampere`), Ryzen 7 3700X.
창 1600×1000, DPR 1, 렌더 비율 2.0, 실제 렌더 타깃 3200×2000, high 품질.
최종 측정은 GPU 강제·차단 우회 옵션 없이 실행했다. 한 번에 하나의 3D 테스트 창만 실행했다.

메모리에서 재사용했으며, 스크린샷은 촬영하지 않았다.

수서동 숲에서는 약 24,029개의 산림 나무를 로딩했다. 회전 900프레임에서는 18ms 초과가
없었고, 자동 비행 897프레임에서는 18ms 초과가 4회였다. 이 숲 장면은 거의 60fps를 유지했다.
숲 측정은 시작 위치를 지역 중심, 지상 120m, yaw -0.75, tilt -0.4로 고정했다. 이 숲 수치는 v14이며 v18 숲을 재측정한 값이 아니다.

**기본 도심 장면은 통과하지 못했다.** 현재 v18 자동 비행에서 678프레임 중 18ms 초과가 211회였고,
95백분위 프레임 간격은 33.5ms였다. 이전 측정의 약 48~56fps보다 이번 수치가 낮다.
공개 API의 타일 로딩과 이동 경로의 장면 구성 차이도 있으므로 단일 실행으로 변경별 개선/악화를 분리해 확정하지 않는다.
CPU 렌더 평균은 9.08ms, GPU 평균은 8.09ms였다. 단위 테스트의 업로드 감소만으로 실제 FPS 향상을 주장하지 않는다.
따라서 일부 숲 장면의 60fps나 단위 테스트 통과를 전체 드론 뷰의 성능 완료로 확대해서 보고하지 않는다.
45fps는 PC 크롬의 해당 고해상도 도심 측정이다. 모바일 실제 기기의 FPS는 측정하지 않았으며,
모바일 세로/가로 화면 검사는 PC Chrome의 터치·화면 크기 에뮬레이션으로 UI를 확인한 것이다.

수서동 초기 진입에서는 첫 네이티브 화면 약 1.2초, 드론 준비 약 4.8초를 확인했다.
초기 50초의 평균은 58.6fps였지만, 최대 프레임 간격 200.2ms와 55~148ms의 긴 작업 5회가
있었다. 초기 로딩 중 모든 프레임이 16.7ms 이하였다고 주장할 수 없다.

남은 병목은 도심 이동 시 렌더링 준비와 차량/보행자 계산이 같은 프레임에 겹치는 부분이다.
로컬 프로파일에서는 주기적 뷰 계산 약 8~9ms와 네이티브 준비 약 8~12ms가 함께 나타났다.
단순 실행 시점 변경은 해결하지 못했다. 화질을 유지한 채 이 비용을 추가로 줄여야 한다.

## 화질·기능 검증

앞선 v14 도심·숲 장면에서 동일 입력과 그림자 상태를 정착시킨 뒤 기존 번들 방식과 객체별 방식을
GPU의 HDR 타깃에서 비교했다. 3200×2000 픽셀 차이는 둘 다 **0**이었으며, 같은 방식끼리의
반복 비교도 0이었다. 처음 연속 프레임에서 관찰한 작은 차이는 고정 입력의 반복 비교에서
재현되지 않았다. 이 검증은 렌더 캐시 방식의 동등성 검사이며, 의도적으로 바꾼 산림 배치를
예전 화면과 동일하다고 주장하는 검사는 아니다.

현재 관련 순수 프런트 테스트 **130개 통과**(106개+차량·교차로 24개), `npx tsc -b` 통과, 독립 Vite 빌드 통과.
테스트는 실제 차량 행렬·색 버퍼 900프레임의 바이트 동일성, 100,000개 충돌 사례,
타이어 높이·다리 층·경계·프로필의 기존 계산과 정확한 비교, 정적 행렬의 부모 이동,
렌더 번들 변경 입력 무효화와 명령 순서, 잎·줄기·LOD·식재 밀도·지형 부착 등을 확인한다.
자동 비행 속도/고도, 시세 표시, 광안대교 및 궁궐 외곽 정원 회귀 검사도 포함한다.
