# Rust/WASM BVH first experiment - 2026-10-04

## Scope and decision

Three.js scene objects/geometry and the existing Tidewater WebGPU renderer
remain the rendering path. There was no existing BVH to port. Road triangle
search used a 6m string-keyed grid. This experiment replaces that broad phase
with a Rust-generated 2D AABB BVH. The exact JS clipping/height calculation is
retained, including road-building masks and paint clearance.

BVH construction runs in a bounded worker; the same packed tree serves paint
workers and runtime tyre-height lookup. A 2-worker forest was implemented and
measured. It builds faster but searches more candidates; one worker gives the
best overall measured CPU result and is the default. The two paint correction
jobs retain their existing parallel execution.

## Controlled CPU measurements

Real rendered asphalt/paint triangles captured from production a258bc6; Edge
155 on Windows, hardwareConcurrency 16, Rust 1.99.0. Seven repetitions per
mode, alternating order, no concurrent build during the final benchmark.
The workload includes index creation, about 10,000 height queries, and both
paint corrections. It is a CPU function benchmark, not page load or FPS.

| Scene | Asphalt triangles | Grid total ms | WASM 1 total ms | Reduction |
| --- | ---: | ---: | ---: | ---: |
| 의정부롯데캐슬골드포레 | 48,138 | 347.3 | 230.2 | 33.7% |
| 신동아파밀리에 | 79,589 | 512.2 | 307.9 | 39.9% |
| 래미안 개포 루체하임 | 87,160 | 542.7 | 317.5 | 41.5% |

Worker time, including bounds preparation and WASM startup:

| Scene | JS BVH 1 ms | WASM BVH 1 ms | WASM BVH 2 ms |
| --- | ---: | ---: | ---: |
| 의정부롯데캐슬골드포레 | 40.0 | 27.3 | 19.5 |
| 신동아파밀리에 | 52.5 | 42.3 | 25.1 |
| 래미안 개포 루체하임 | 54.2 | 46.0 | 28.1 |

The largest gain comes from selecting fewer candidate triangles, not merely
changing language. The JS BVH control also improves substantially. WASM 2
total times were 231.3 / 317.7 / 330.1ms; query/paint traversal offset its
construction gain. Every sampled height and every corrected paint float
matched the grid result in all controlled cases.

## Whole-scene A/B and practical limits

Same production-config frontend, data/camera/hour, with `bvh=grid` versus
default WASM 1. Two scenes, three measured pairs each, both modes warmed first.
Actual readiness includes trees, roads, traffic, water, actors and a ready
renderer. Times below are medians from selection to readiness.

| Scene | Road grid → WASM | All ready grid → WASM | All ready change |
| --- | --- | --- | --- |
| 의정부롯데캐슬골드포레 | 6.739 → 6.803s | 7.002 → 7.098s | +1.4% |
| 래미안 개포 루체하임 | 8.467 → 8.163s | 8.719 → 8.505s | -2.4% |

Steady frame median was 16.7ms (about 60 fps) in both modes. Pointer-to-next-frame
p95 medians were 12.5→17.2ms and 9.1→10.6ms. These small samples do not show an
input-latency or FPS improvement. Scene loading has network/model/scheduling
variation; no consistent whole-scene gain or statistical significance is
claimed. The 7-second full-load target is not achieved across scenes. Physical
iPad FPS was not measured.

All six measured A/B pairs had identical asphalt and paint position hashes.
The first Ganeung warmup had different upstream asphalt counts (48,138 versus
46,998); warmup was excluded and is recorded rather than claimed identical.
Measured pairs are individually compared so different upstream inputs cannot
masquerade as a geometry regression or performance gain.

## Cost, safeguards and tests

- WASM binary 28,085 bytes; gzip 10,969 bytes. No additional external provider
  requests, geometry simplification, texture replacement, or renderer change.
- Retained packed indexes on the controlled fixtures: 716,808 / 1,366,900 /
  1,397,184 bytes. This is index storage, not total GPU or process memory.
  Original grid heap was not measured. Worker WASM memory is released on exit.
- Original GPU attributes are never detached/reordered. Stale generations
  cannot install a result. Owner abort/last-view release terminates workers.
- WASM unavailable, invalid geometry, failure or 1-second timeout returns the
  verified grid path. iPad/touch-Mac and <=4GB devices use at most one worker
  and skip BVH above 250,000 triangles; general cap is 2,000,000.
- 81 relevant automated tests passed. Chromium, WebKit and iPad-emulated WebKit
  passed cancellation, zero-live-worker, blocked-WASM fallback and restore
  tests. This is browser compatibility evidence, not a physical-device FPS test.
- Actual WebGPU road line audits on Ganeung/Shindonga/Luceheim passed with no
  missing or buried paint samples; pre-deployment JSONs are `tmp/bvh-coverage-*`.

## Next candidates requested by the user

| Candidate | Recommended role |
| --- | --- |
| Geometry | First WASM candidate for loading: triangulation, road/ground clipping, normals, indexing and mesh merge in large typed-array batches. |
| Quadtree | Spatial cells serving culling/LOD/loading; low standalone value if all objects are still submitted. |
| Culling | High FPS potential by reducing off-screen GPU work; spatial grouping and conservative bounds matter more than a language swap. |
| LOD | Screen-size/distance detail policy coupled with spatial culling; preserve near/selected buildings and stable transitions. Scalar distance tests alone gain little from WASM. |
| Instance update | Batch moving-car/wheel/pedestrian matrix work; reduce dirty buffer uploads. Static trees should not be updated every frame. |
| Path finding | Lower priority for normal map viewing; route requests are occasional. Reassess for many simultaneous dynamic routes. |

Current code has explicit `frustumCulled=false` on some batches and repeated
dynamic `instanceMatrix.needsUpdate` paths. Profile before extending scope.
Loading priority: Geometry. GPU/iPad priority: Quadtree+Culling+LOD. CPU frame
priority: Instance update. No unmeasured multiple is promised.
