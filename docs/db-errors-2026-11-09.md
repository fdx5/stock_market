# 콘솔 5xx / DB 오류 증폭 개선 (2026-11-09)

## 증상
관리자 콘솔(SYNAPSE·Atlas 모니터)에 5xx가 간헐적으로 표시됨.
DB 오류는 이미 503으로 바뀌어 응답되므로 콘솔에서는 "5xx"로 집계된다.

## 원인 (코드·장애 주입으로 확인)
1. **재연결 시 스키마 전체 재실행.** 문 하나가 실패하면 모든 스토어가 `_new_ready_connection()`을 다시 불러
   CREATE/PRAGMA/ALTER 10~30개를 락을 쥔 채 다시 보냈다. HTTP 파이프라인에서 "재연결"은 세션 객체일 뿐이라 의미가 없고,
   그 사이 같은 스토어 호출이 게이트 대기(4초)를 넘겨 503으로 연쇄 실패했다.
2. **Turso 엣지 502 "upstream forward failed"는 재시도 없음.** 읽기도 즉시 실패했다.
3. **SQL 문 자체 오류도 브레이커에 집계.** 제약조건 위반 등 4번이면 해당 스토어 전체가 25초간 503이었다.
4. **타임아웃된 쓰기를 스토어 단에서 다시 보냄.** 중복 기록 위험이 있었다(prediction/mail 스토어는 최대 3회).
5. `support_comment_store` 초기화 중간 실패 시 반쯤 만들어진 연결이 남아, 재시작 전까지 "no such table" 오류가 났다.

## 수정
- `turso.py`
  - `TursoUnreachable`(연결·5xx·429)과 문 오류(`TursoError`)를 구분했다.
  - 멱등 DDL(`CREATE … IF NOT EXISTS`)과 `PRAGMA table_info`는 프로세스당 1회만 보낸다(ALTER/DROP 시 무효화).
  - 429·502·503은 읽기·쓰기 모두 1회 재시도하고, 500·504는 읽기만 재시도한다.
  - `should_retry()`: 스토어 재시도는 연결 단계 오류일 때만 한다.
- `libsql_gate.py`: 브레이커는 연결 장애만 집계한다.
- 모든 스토어의 재연결 루프는 `turso.should_retry`를 먼저 확인한다.

## 측정 (`backend/scripts/db_fault_harness.py`, 15% 장애 주입, 관리자 API 152회, 캐시 콜드)
| 장애 | 이전 실패율 | 이후 실패율 | DB 왕복 |
|---|---|---|---|
| Turso 502 | 10.5% | 3.3% | 594 → 417 |
| 연결 리셋 | 2.6% | 0.7% | 559 → 441 |
| 읽기 타임아웃 | 2.6% | 3.3% | 559 → 417 |

타임아웃이 소폭 늘어난 것은 시간 초과된 쓰기를 더 이상 다시 보내지 않기 때문이다(중복 기록 방지, 의도된 변화).

## 별건
`/api/discovery/derivatives`는 Bybit 원천 거부로 운영에서 항상 502를 반환한다. DB와는 무관하지만 콘솔 5xx에 계속 집계된다.
